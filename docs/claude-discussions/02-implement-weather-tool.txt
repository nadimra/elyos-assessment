     Plan: probes/probe_weather.py

     Context

     The chat app (main.py) is being built against two undocumented-quirk APIs.
     Before wiring /weather into the LLM tool loop, we want a standalone probe
     that systematically maps the endpoint's real behaviour — happy path, name
     disambiguation, input parsing, adversarial inputs, auth, and the rate
     limiter (~4 req / 30 s observed).

     The findings will be folded into docs/api-notes.md afterwards and will
     shape the error handling we add to get_weather() in main.py. This plan
     covers only the probe; it does not touch main.py.

     File to create

     - probes/probe_weather.py — single standalone Python script.

     No changes to main.py, requirements.txt, or anything else.
     httpx is already installed transitively via anthropic (verified:
     0.28.1 in .venv), so no new dependency.

     Approach

     Single sync script (httpx.Client) — rate limiting makes async pointless
     and a linear top-to-bottom script is easiest to debug.

     Structure:

     1. Load ELYOS_API_KEY from .env via python-dotenv.
     2. Define BASE_URL and a small probe(name, params, *, method="GET", 
     headers=None) helper that records: name, request URL/params, status,
     elapsed ms, response headers, parsed JSON (or raw text on parse fail),
     and any exception.
     3. Group probes into ordered "batches" of 3 calls each, then sleep(32)
     between batches — one head-room request below the observed 4-call
     limit, and 2 s above the 30 s recovery window.
     4. One dedicated burst batch that intentionally fires 6 rapid requests
     to capture the limiter's status code, Retry-After / X-RateLimit-*
     headers, and body. Then sleeps 35 s and re-fires one request to confirm
     recovery.
     5. Write everything to probes/probe_weather_results.json (full
     request/response detail). Console output is minimal: one line per
     probe ([ok|FAIL|429] case-name (123ms)) and a final summary.

     Probe catalogue (~45 cases, ordered safest → riskiest)

     Happy path (baseline shape + latency)
     - London, Tokyo, New York

     Ambiguous / duplicate names (which one wins?)
     - Springfield, Cambridge, Boston, Newcastle, Athens, Tripoli

     Case / whitespace / punctuation / encoding
     - LONDON (upper)
     - london (lower)
     -  London  (padded — does it strip?)
     - London,UK (no space qualifier)
     - London, UK (space qualifier)
     - London, Ontario (force disambiguation away from default)
     - ?location=London&location=Tokyo (repeated param — which wins?)

     Adversarial / quirky inputs
     - "" empty string
     - omit location param entirely
     - different param name (?city=London)
     - 1000-char string ("a" * 1000)
     - Unicode native: 東京, Москва, São Paulo
     - emoji: 🗼
     - numeric: 12345
     - coordinates: 51.5074,-0.1278
     - SQL-ish: London'; DROP TABLE cities;--
     - HTML/XSS-ish: <script>alert(1)</script>
     - fictional: Atlantis, Hogwarts, Asdfjklqwerty
     - postal code: SW1A 1AA
     - airport code: LHR
     - country only: France
     - continent: Europe
     - comma-joined cities: London,Tokyo
     - newline injection: London\nTokyo

     Auth / method
     - missing X-API-Key header
     - wrong X-API-Key value
     - POST /weather?location=London (wrong method)

     Determinism (response stable across calls?)
     - call London 3× spread across different batches, diff JSON bodies in
     the post-run summary

     Rate-limit burst (dedicated batch, run LAST so prior probes aren't
     contaminated by an active limiter)
     - 6 rapid London calls back-to-back, capture every status + headers
     - sleep(35)
     - 1 final London call to confirm recovery + measure post-recovery latency

     Pacing math

     ~45 normal probes ÷ 3 per batch = 15 batches × 32 s ≈ 8 min, plus
     burst+recovery ≈ +40 s. Total run ≈ 9 minutes. Acceptable for a
     one-shot exploration.

     Output schema (probes/probe_weather_results.json)

⏺ The probe surfaced a lot — here's what stood out.

  Headline findings

  1. Rate limit hides inside a 200 response (the biggest gotcha)

  The 6th rapid call returned HTTP 200 with body:
  {"status": "throttled", "message": "Rate limit exceeded. Please wait.",
   "retry_after_seconds": 29, "data": null}
  There is no 429. A naive integration that checks status_code == 200 then reads
   response["location"] will crash. The chat tool must inspect the body and look
   for status: "throttled" / data: null. The retry_after_seconds field tells you
   how long to wait. Observed limit: ~5 requests per ~30 s window.

  2. Two completely different response shapes for happy 200s

  - Single result: {location, temperature_c, condition, humidity}
  - Multi result: {location, conditions: [{...}, {...}], note: "Multiple 
  conditions reported"} — the temp/humidity keys move into a nested list.

  Both happened to common queries (Cambridge, Tripoli, "London, UK", SW1A 1AA,
  São Paulo, Москва). Plus the throttled shape above. So callers must handle
  three possible 200-body shapes.

  3. Ambiguity handling is inconsistent and qualifiers are unreliable

  ┌────────────────────────────────┬────────────────────────────────────────┐
  │             Input              │             What came back             │
  ├────────────────────────────────┼────────────────────────────────────────┤
  │ Springfield, Boston,           │ silently picks one (no warning)        │
  │ Newcastle, Athens              │                                        │
  ├────────────────────────────────┼────────────────────────────────────────┤
  │ Cambridge, Tripoli             │ multi-result with both                 │
  ├────────────────────────────────┼────────────────────────────────────────┤
  │ London, UK                     │ multi-result with two Londons          │
  │                                │ (qualifier ignored)                    │
  ├────────────────────────────────┼────────────────────────────────────────┤
  │ London, Ontario                │ correctly disambiguates to Ontario     │
  └────────────────────────────────┴────────────────────────────────────────┘

  4. Geocoder is far more permissive than documented

  - 12345 → Schenectady (zip-code lookup)
  - 51.5074,-0.1278 → "Strand" (coords resolve to neighborhood, not "London")
  - London'; DROP TABLE cities;-- → "Tiar Drop" (fuzzy match on fragments)
  - <script>alert(1)</script> → "Alert" (grabbed the word)
  - Atlantis, Hogwarts → both returned data (some real place matched fuzzily)
  - France → returned Paris (silently picked capital)
  - LHR → "London Heathrow Airport" (airport codes work)
  - SW1A 1AA → multi-result London (postcodes work but ambiguously)

  5. Error shapes are inconsistent (3 different schemas)

  ┌──────────┬────────────────────────────────────────────────────────────┐
  │  Status  │                           Shape                            │
  ├──────────┼────────────────────────────────────────────────────────────┤
  │ 401, 404 │ {"error": "..."}                                           │
  ├──────────┼────────────────────────────────────────────────────────────┤
  │ 422      │ {"detail": [{type, loc, msg, input}]} (FastAPI validation) │
  ├──────────┼────────────────────────────────────────────────────────────┤
  │ 405      │ {"detail": "Method Not Allowed"} (string, not list)        │
  └──────────┴────────────────────────────────────────────────────────────┘

  A single parse_error() helper must handle all three.

  6. Other notable behaviours

  - Case + whitespace normalised: LONDON, london, "  London  " all return
  identical London (9.2°C).
  - Repeated ?location=: last value wins (?location=London&location=Tokyo →
  Tokyo).
  - Comma-joined cities: London,Tokyo → Tokyo (last wins again).
  - Newline injection: London\nTokyo → Tokyo (newline truncates first value).
  - 404 echoes input verbatim in error field (the 1000-char "aaaa…" came back in
   full — potential XSS sink if rendered as HTML).
  - Unicode: 東京 → 東京都 (prefecture appended); São Paulo → Sao Paulo (accent
  stripped); Москва works.
  - 401 is fast (~16 ms) — doesn't touch the weather backend or rate limiter.
  Useful for failing fast on bad keys.
  - London temperature drifts: 9.2 → 9.4 → 9.4 across the run, so responses are
  not perfectly cacheable.

  What this means for the chat app

  When wiring get_weather() into main.py, the tool wrapper needs to:
  1. Always check body.get("status") == "throttled" on 200 responses — retry
  after retry_after_seconds or surface the wait to the user.
  2. Normalise both 200 shapes into one (pick first condition from conditions[]
  and warn the LLM there were multiple matches — that's useful signal to ask the
   user "did you mean Cambridge UK or MA?").
  3. Map 4xx into intelligible error messages by detecting which of the three
  error shapes was returned.
  4. Not blindly trust the location echo — 12345/<script> returning a real place
   is misleading.
