     Probe /research endpoint

     Context

     docs/interview.md exposes two APIs; PR #2 already probed /weather
     (probes/probe_weather.py → probes/probe_weather_results.json) and filled
     out the /weather section of docs/api-notes.md. The /research section of
     that file is a skeleton (lines 114–123) and research_topic in main.py is
     not yet implemented. Before implementing the tool, we want the same
     evidence base: a systematic probe script, raw results, and a written-up
     quirks list.

     /research differs from /weather in ways the probe must account for:

     - Latency 3–8 s per call (per docs) — total runtime is much longer, and
     pacing needs to budget API time, not just sleep time.
     - Free-form topic semantics rather than geocoded names — so the interesting
      axes are topic length/shape, language, sensitivity, and response
     variance/structure rather than ambiguous place names.
     - The endpoint we most need to cancel from — so understanding latency
     distribution and how the server behaves on client disconnect/timeout is
     directly load-bearing for the implementation.

     Approach

     Create probes/probe_research.py modelled on probes/probe_weather.py:1 (same
      probe() helper, batching, results envelope, KeyboardInterrupt-safe finally
      write). Run it once, then write up findings into the /research section of
     docs/api-notes.md.

     Reused infrastructure from probe_weather.py

     - _headers_for(auth) (probe_weather.py:44) — valid / missing / wrong
     - probe(name, category, params, method, auth, pace) (probe_weather.py:54) —
      same record schema (status, elapsed_ms, response_headers, response_body,
     error)
     - force_batch_break() (probe_weather.py:117) — clean window before the
     burst
     - write_results() summary (probe_weather.py:199) — by-status counter,
     determinism check, burst summary
     - client = httpx.Client(timeout=30.0) — needs to bump to ~60s since
     research can take up to ~8s and we want headroom for slow/error cases. Set 
     timeout=60.0.

     Pacing tweak

     Weather pacing is "3 requests per 32 s window". For research, each call
     eats 3–8 s of that window. Worst case: 3 calls × 8 s = 24 s of API time
     inside a 30 s window — already brushing the limit. Be more conservative:

     - BATCH_SIZE = 2, BATCH_SLEEP = 32 — gives ~16 s slack inside the
     rate-limit window even when all three calls hit the 8 s ceiling.
     - Keep BURST_RECOVERY_SLEEP = 35.

     Probe cases (~37 calls)

     The categories mirror the weather probe but the contents are
     research-specific.

     Happy path (3) — broad topics likely well-formed in the server's response
     template:
     - solar energy (docs example)
     - climate change
     - quantum computing

     Topic shape / formatting (6) — see how topic is parsed:
     - case-upper: SOLAR ENERGY
     - case-lower: solar energy
     - ws-padded:  solar energy 
     - plus-encoding: solar+energy (docs use ?topic=solar+energy — does + become
      space, or literal +?)
     - multi-word: the history of quantum computing in europe
     - repeated-param: ["solar energy", "wind energy"] (last-wins like weather?)

     Adversarial (10):
     - adv-empty: ""
     - adv-no-param: no params at all
     - adv-wrong-paramname: {"query": "solar energy"}
     - adv-long-2000: "a" * 2000 — way past any reasonable topic
     - adv-unicode-jp: 太陽光発電
     - adv-emoji: ☀️🔋
     - adv-numeric: 12345
     - adv-gibberish: qwerasdfzxcv
     - adv-sql: solar'; DROP TABLE topics;--
     - adv-xss: <script>alert(1)</script>

     Sensitive / open-ended (3) — see if there's any content filter or refusal
     envelope (relevant because the LLM will pass arbitrary user text through):
     - topic-controversial: bioweapons synthesis
     - topic-personal: my neighbour John Smith
     - topic-empty-question: ?

     Auth / method (3):
     - auth-no-key
     - auth-wrong-key
     - method-post with topic=solar energy

     Rate-limit burst (4) — fewer than weather (each call is slow, and we
     already know the 200-with-throttled-body pattern from weather; we just want
      to confirm it applies here too):
     - 4 back-to-back calls with pace=False, then BURST_RECOVERY_SLEEP, then one
      recovery call.

     Latency / cancellation (7) — characterise the 3–8 s claim directly:
     - latency-sweep-1..6: same topic (solar energy) called 6 times back-to-back
      under normal pacing (not a burst — we want representative latencies, not
     throttled ones). Feeds min/max/mean/p50/p95.
     - cancel-timeout: one call with timeout=1.0, recording the ReadTimeout
     exception. Mirrors what client-side cancellation will look like in
     research_topic. Tagged in its own category so it doesn't pollute the
     latency stats.

     Note: latency-sweep-* doubles as additional determinism samples for solar 
     energy, so the existing three determ-solar-* slots can be dropped —
     comparison happens across all 7 sweep bodies instead.

     Output

     probes/probe_research_results.json, structurally identical to the weather
     one, plus:
     - latency_stats for happy-path 200s: min / max / mean / p50 / p95 in ms
     - solar_responses_identical (analogous to london_responses_identical)
     - Record the timeout case under its own category so write_results can list
     it without skewing latency stats.
